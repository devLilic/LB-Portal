# MOS mapping editor

## Current scope

The per-project **Mapări CSV OnAir** tab configures mappings separately from MOS sources. It discovers graphic type/template pairs from the already-loaded OnAir snapshot, resolves them to existing sections and A/B target templates, and maps CSV fields to one or more LiveBoard fields per target. Source template names remain those exported by csvEditor-PA. Saving follows the normal project draft/validation flow and does not execute graphics. See [OnAir CSV](CODEX_ONAIR_CSV.md) for supported CSV parameters, validation, duplication and the value preview.

The CSV source panel also configures project-specific default templates for locations and phone interventions whose rows have no template. A nonblank CSV template always takes precedence. The detected-source catalog and OnAir preview use the same effective-template helper; changing defaults in the draft immediately updates the catalog without rereading CSVs.

The project editor now separates Sections from [Interactions](CODEX_SECTION_INTERACTIONS.md). Section configuration groups destinations/buffers, timing and source field/exit settings; project rules select existing sections and ordered lifecycle actions. The wider responsive page keeps the edited project separate from the active runtime selection. A rule's automatic return uses the existing source duration, without a second duration field.

The Settings / MOS mappings page configures the [LiveBoard execution controller](CODEX_LIVEBOARD_EXECUTION.md). Saving settings does not play a template. If a save is blocked by active sections, the editor stops each affected section through the regular controller queue and retries once; failures keep the draft and show an error. Accepted mapped MOS PLAYs execute in simulation by default, or through manually connected LBC TCP. The console remains available in its own tab; the HTTP envelope and receipt acknowledgement remain unchanged.

The console folds the configured section list, and each compact section card hides buffer fields and local resync inside a disclosure. Received request rows expose a one-line result, time and section/template context by default; full mappings and execution steps expand on demand. Active status, actions and failure signals stay visible in the compact view.

For section editing, the section name and delete action appear above the numbered steps. Identity/destination settings (step 1) and timing settings (step 2) share a row when the editor column is at least 1200 px wide. Step 1 receives the larger column and the section name field is capped at 32 rem. Each destination and each timing control occupies its own row, while source mapping (step 3) remains full width for its field table. Below that width the first two steps stack.

## Sections and sources

Sections belong to independent [projects](CODEX_MOS_PROJECTS.md). Telejurnal and Retrospectiva săptămânii accept Plasma sources; standalone projects may save sections with no Plasma sources for their later direct-operation interface. Selecting the project to edit does not activate it.

Section rows include accessible move-up/move-down controls. They reorder the draft without changing the selected section or interaction references; explicit Save persists the order used by the editor and console. An order-only change preserves active runtimes, buffers and timers without sending LiveBoard commands. The project selector also offers Duplicate project: it selects an independent standalone copy with an editable name, fresh internal IDs and remapped field/interaction references while retaining all configuration values and ordering. Copies are saved explicitly and do not activate automatically. Built-in project identities remain fixed.

Each named section owns one or two LiveBoard destinations and one or more Plasma source templates. Two destinations represent alternating buffers shared by all sources in that section, for example Plasma `01_Titlu` with LiveBoard `01_Titlu-1` and `01_Titlu-2`.

Each source has a table mapping exact Plasma parameter names to one or more LiveBoard fields for each destination. Enter one destination field per line, or repeat a source parameter on multiple rows; the same source value is sent to every listed field, such as `Titlu` → `Titlu` and `Titlu_M`. A cell may be left empty, and source parameters with no destination fields are ignored and are not required in PLAY requests. A parameter mapped for a destination remains required when that destination is selected. These mappings are used only for PLAY; RESUME always uses only the resolved destination template name and never requires mapped parameters. Destination field names can differ between buffers. Graphic-only templates may have an empty table. Template and field names retain their spelling, case, accents, and punctuation. Stable internal IDs preserve field relationships when destination names change.

For paired destinations the RESUME-to-PLAY delay is selectable from `0, 50, 100, 150, 200, 250, 500, 1000` ms, initially `100`. A separate data propagation delay is selectable from `0, 100, 250, 500, 1000` ms, initially `250`. Older version-1 configurations without `dataPropagationDelayMs` use 250 ms. Each destination receives the complete mapped set before its PLAY; only the hidden destination is rewritten during an A/B swap.

Each source selects manual exit through RESUME or automatic exit performed by its LiveBoard template. Automatic duration is positive seconds, initially `6`. LB-Portal uses it to estimate local OFF, without sending RESUME or STOP on expiry; the real exit remains inside the template.

## Suggestions and persistence

The canonical `mosMappings` setting is now version `2`: projects and the active project ID, with each project's section mappings retaining the inner version `1` structure described below. Legacy flat configurations migrate in memory into Telejurnal without changing IDs or technical names; Retrospectiva starts empty. The old flat preload methods adapt the active project's mappings and preserve other projects on write. The editor uses full project read/save operations. Suggestions are scoped to the edited project's saved/draft mappings and accepted requests captured for that project.

The console uses saved settings, never editor drafts. The immutable mapping snapshot contains all configured targets, each parameter, field and received value for PLAY; RESUME reports that it uses only the template name and does not show PLAY field mappings as missing. A separate evolving execution report shows the chosen target and ordered steps. Missing and extra PLAY parameters are identified; a missing PLAY parameter blocks execution, while an empty string is valid. Graphic-only templates have no invented fields. Unknown/malformed requests or unavailable settings are explicit diagnostics. Historical mappings do not change after edits; TCP acknowledgements do not imply physically observed output.

Plasma template and parameter suggestions combine the edited project's saved/draft configuration with valid accepted `mos-play` requests captured for that project. Unknown templates also retain the project at receipt, so their suggestions cannot cross into another project's editor. Rejected and malformed requests provide no suggestions. Clearing/restarting the console removes unsaved observed suggestions; saved mapping names remain available. Operators can always enter names manually; LiveBoard names are entered manually.

Each project's inner mapping object remains version `1`. Fresh installations include empty Telejurnal and Retrospectiva projects; older section lists are preserved inside Telejurnal. Main owns file access and validation; preload exposes typed project operations and the legacy `settingsApi.getMosMappings()` / `settingsApi.setMosMappings()` adapters. Settings are explicitly saved, and leaving the editor with unsaved changes prompts the operator.

Saving rejects malformed structures, empty required identifiers, duplicate source template assignments, conflicting destination ownership, duplicate field names within a destination, and invalid delays or durations. Repeated source parameter rows are valid and combine into one-to-many mappings. Empty field lists are valid, and legacy single-field settings remain readable. Save errors retain the draft and do not report success.

### Expected save restrictions

An active/uncertain section or queued/running operation can temporarily block saving. These restrictions are operational outcomes, handled as typed IPC data rather than rejected `settings:set` handlers. Main returns a denial code (`MOS_MAPPINGS_ACTIVE`, `LIVEBOARD_CONNECTION_ACTIVE`, or `LIVEBOARD_BUSY`) and the affected section names. A denied setting is neither written nor applied to runtime.

The editor uses `settingsApi.trySaveMosProjects()` and `trySaveLiveBoardConnection()`, displays localized instructions, retains its draft and re-enables Save. The legacy `trySaveMosMappings()` adapter remains available. It does not show an IPC exception prefix or a success notice for the denied attempt. Existing setters preserve their compatibility contract, but convert denial to a plain rejection in preload; they no longer make the main handler throw for an expected restriction. Unexpected programming, storage and sender-validation errors remain real errors; do not silence Electron logging globally.

Run focused mapping, persistence, controller, transport and ingress tests plus the LB-Portal build. Verify single/paired targets, multiple sources, one-to-many field fan-out, intentionally unmapped source parameters, graphic-only templates, renaming, dirty navigation and restart persistence.
